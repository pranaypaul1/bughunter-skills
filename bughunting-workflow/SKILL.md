# Bug Hunting Workflow

This is the hunter's end-to-end methodology, organized into phases. Each phase lists what to do and which *kind* of technique skill to reach for at that point. This file is deliberately not an exhaustive technique library — it's the spine. Specific techniques live in their own **topic** skills (one per vuln class/category, e.g. `race-condition-testing`), which accumulate entries from multiple source writeups over time. `loxs-medium` and `loxs-hackerone` are not technique skills themselves — they're source logs (one for Medium/infosecwriteups articles, one for HackerOne public disclosed reports) tracking which sources have been processed and which topic skill each one fed into (see either skill for its ingestion process; both route into the same topic-skill pool). This file doesn't need editing every time a new technique or article/report is learned; only when a genuinely new topic category is created (add it to "Linked technique skills" below).

## How to chain in technique skills

Before or during each phase below, check the list of skills currently available in this session. If a skill's name or description matches the phase you're in (e.g. a skill about subdomain enumeration during Recon, or a skill about IDOR during Vuln Testing), consult it and apply its techniques at that point. New technique skills get picked up automatically this way — nothing here needs updating when one is added. If unsure whether a skill is relevant, err toward checking it; the cost of looking is low.

## Phase 0 — Program Intake & Scope Capture

Goal: before touching anything, pin down exactly what's in scope and save it somewhere durable — this always runs first, whenever the hunter pastes a new program URL (Bugcrowd, HackerOne, Intigriti, a private/company-run program page, etc.) alongside this skill.

1. **Check for an existing folder first.** Look under `/home/pranay/Documents/HunterY/` and `/home/pranay/Documents/HunterZ/` for a folder matching the target/program name — this hunter runs one folder per target, split across those two directories (see `agy-hunterz`/`HunterB15` too if not found there). If it already exists, read `notes/scope.md` there and treat this as a re-scope/update rather than a fresh intake.
2. **Fetch the program's scope page.** Use WebFetch first; if it's JS-paginated/gated behind login (common on Bugcrowd/company-run portals), fall back to Chrome browser automation (load `mcp__claude-in-chrome__*` core set) to read the rendered page while authenticated in the hunter's real browser session.
3. **Extract and record:**
   - Program type/platform, testing period, disclosure policy, safe-harbor notes.
   - Full in-scope list: every domain and its in-scope subdomains (or wildcard), mobile apps (iOS/Android package/bundle IDs), API surfaces — note any per-target severity/engagement tag the program itself uses (e.g. "High engagement").
   - Full out-of-scope list, called out explicitly — pay special attention to near-miss traps (a sibling domain that looks in-scope but isn't, a deprecated subdomain carved out of an otherwise in-scope domain).
   - Program-level excluded vulnerability classes/report types (the program's own "won't accept" list) — this prevents wasted effort chasing a class the program has pre-rejected.
   - SLA targets and reward bands per severity, plus any active bonus periods.
   - Any required test-account setup (a specific signup email domain, a "developer mode" toggle, sandboxed test data requirements).
4. **Create the target folder and save scope.md.** If no folder exists yet, create one under `HunterY` (default — ask the hunter only if they want it under `HunterZ`/elsewhere instead) with the standard per-target layout already used across existing targets: `notes/`, `recon/`, `source/`, `javascript/`, `requests/`. Write the scope into `notes/scope.md` using the format already established across existing targets (see `nykaa/notes/scope.md` and `etsy/notes/scope.md` for the reference shape):
   ```markdown
   # <Target Name> — <Platform> Bug Bounty Scope
   Source: <program URL>, pulled <date>

   ## In-Scope
   ### <domain>
   <subdomains, or *.domain wildcard, with any engagement-tier notes>
   ### Mobile apps
   <package/bundle IDs per platform, if any>

   ## Out of Scope
   <explicit list, including deprecated/carved-out subdomains and lookalike sibling domains>

   ## Program-level out-of-scope vuln classes
   <the program's own excluded-report-types list>

   ## SLA / Rewards
   <per-severity SLA and reward bands, bonus periods if any>
   ```
5. **Only after scope.md is saved**, proceed into Phase 1 below. Every later phase should stay inside what `scope.md` says is in-scope — re-check it before testing any newly-discovered subdomain/asset, since Phase 1 recon routinely surfaces hosts not explicitly listed in the program page.

## Phase 1 — Recon & Asset Discovery

Goal: build the widest accurate map of what belongs to the target before touching anything. Run as a staged pipeline — each stage's output feeds the next — mirroring the reference checklist recorded in `recon-scanning-toolkit` (source: [Recon to Master: The Complete Bug Bounty Checklist](https://infosecwriteups.com/recon-to-master-the-complete-bug-bounty-checklist-95b80ea55ff0)). Don't skip stages because an earlier one looked thin — each surfaces assets/leads the others structurally can't.

Treat every stage's output as feeding one master file (e.g. `all-assets.txt`), not a disposable intermediate — the highest-value findings usually come from manually cross-referencing entries *across* sources rather than reading any one tool's output in isolation (e.g. a subdomain from passive DNS + a staging-environment hint from an HTTP response + a leaked bucket reference from a GitHub repo + a credential from a backup file found via directory fuzzing is one chain, not four unrelated leads). Recon is the majority of the actual work here; resist treating it as a box to check before "real" testing starts. (Source: [You Won't Find Any Vulnerabilities Without This Technique](https://osintteam.blog/you-wont-find-any-vulnerabilities-without-this-technique-65da99920b64) — folded in here rather than a dedicated skill since every individual tool/source it names is already covered in depth by `recon-scanning-toolkit`/`github-recon-testing`/`cloud-storage-bucket-testing`.)

### 1a. Subdomain enumeration
Automated tools (subfinder/assetfinder/findomain/chaos/amass, passive + active) merged with manual public sources (Certificate Transparency/crt.sh, Wayback Machine, VirusTotal, HackerTarget, URLScan.io, CommonCrawl), plus GitHub subdomain scraping and Shodan-powered subdomain search, subdomain permutation + DNS resolution, and FFUF brute-force as the catch-all. Never rely on a single source — each tool/source finds subdomains the others miss. → `recon-scanning-toolkit`'s "Subdomain enumeration — additional sources" section has the exact command chain.

### 1b. Infrastructure discovery
ASN/IP mapping and pivoting (surfaces infrastructure the target owns but never linked from a subdomain — old/forgotten hosts) and live-host identification with tech-detect (the highest-value flag here — it tells you the framework/CVE surface before writing a single payload). If the target sits behind a known WAF/CDN, run `waf-origin-ip-discovery-testing` now rather than waiting for Phase 3 — origin-IP discovery is cheap infra-level recon, and having it in hand before payload testing starts avoids fighting WAF signatures one-by-one later. → `recon-scanning-toolkit`'s "ASN / IP pivoting" section.

### 1c. Visual & URL reconnaissance
Screenshot every live host (fast triage of login portals/admin panels/error pages across hundreds of hosts) alongside active crawling and passive/historical URL collection (wayback/gau/CDX API — see `recon-scanning-toolkit`'s Wayback Machine CDX API deep-dive for the full technique, including PDF-content keyword scanning and deleted-file 404 recovery), merged into one deduplicated URL list, then parameter extraction + `gf` pattern filtering to pre-triage URLs by likely vuln class before any payload is sent. → `recon-scanning-toolkit` techniques #1/#3 and the CDX API section.

### 1d. Content analysis
Automated vulnerability scanning (nuclei, critical-severity triage pass first), sensitive-file discovery via extension/regex sweep, hidden-parameter discovery (Arjun — feeds directly into `http-parameter-pollution-testing` and `mass-assignment-testing` once found), directory/file brute-forcing, and JS-file discovery + bulk secret/endpoint extraction. → `recon-scanning-toolkit` techniques #4/#5/#11 and the JSRecon section.

### 1e. Specialized platform testing
If tech-detect flags WordPress: run wpscan (themes/plugins/users enumeration) and check `/xmlrpc.php` reachability → `xmlrpc-abuse-testing` for the full attack surface that single endpoint exposes (brute-force amplification, SSRF/DDoS via pingback, port scanning, legacy-library RCE). → `recon-scanning-toolkit`'s "WordPress-specific scanning" section.

### 1f. Network-level reconnaissance
Port scanning — naabu for fast initial discovery across many hosts, nmap for deep service/version detection on the ports that matter, masscan only when full-range speed across a huge IP set is needed. → `recon-scanning-toolkit`'s "Port scanning" section.

### Cross-cutting, run throughout every stage above
- Map out API surfaces: `/api`, GraphQL endpoints, mobile app backends, Swagger/OpenAPI docs (→ `swagger-ui-xss-testing` if found — the `configUrl` parameter is a recurring DOM XSS vector on exposed Swagger UI instances).
- GitHub recon for leaked secrets/credentials (→ `github-recon-testing`) as a standing parallel track, independent of how hardened the live app itself is.
- Cloud storage bucket recon (→ `cloud-storage-bucket-testing`) whenever the stack references AWS S3/Azure Blob/GCS.
- Note anything unusual: staging/dev subdomains, exposed admin panels, cloud storage buckets, old versions.
- Treat DNS enumeration as high-value, low-noise recon, not just an inventory step: DNS records rarely get cleaned up, so stale/forgotten subdomains (`dev.`, `old-api.`, `backup01.`, `vpn.`) are often the easiest way to find a liability nobody's watching anymore — a legacy or staging host discovered this way is frequently softer-target than the production surface. It's also effectively invisible to most defensive monitoring (port scans and payload-based IDS rules don't watch DNS query patterns), so it's worth doing thoroughly before any noisier active testing starts.
- If the target has an Android/iOS app in scope, pull the APK/IPA now (via ADB from an installed device, or APKMirror/APKPure) — it feeds `mobile-app-testing` in Phase 3 and is often faster to get high-severity findings from than the web surface, since mobile client code frequently contains hardcoded secrets and reveals undocumented API endpoints.

Consult any linked skill about recon tooling or subdomain techniques here.

## Phase 2 — Enumeration & Prioritization

Goal: turn the asset map into a ranked list of what's worth testing first.

- Screenshot and triage live hosts by apparent value (auth portals, payment flows, admin panels > static marketing pages). When triaging a large `httpx` output specifically, grep subdomain names first for `admin`, `api`, `dev`, `test`, `internal`, `staging` — these naming patterns disproportionately lead to misconfigurations/exposed panels/weak security and are worth opening manually before anything else. Once inside a target, don't rely on automation alone: manually click through every distinct page/flow, watch DevTools' Network tab for endpoint patterns (`/api/`, `/v1/`, `/internal/`, `/graphql`) as you go, and note anywhere the page handles user data/IDs/uploads/forms — most real bugs here turn out to be weak logic/missing checks/bad assumptions (e.g. `id=123` → `id=124`, dropping a required parameter, submitting unexpected input) rather than anything requiring a specialized tool. (Source: [What I Look For After httpx](https://medium.com/bug-bounty-hunting-a-comprehensive-guide-in/what-i-look-for-after-httpx-a462dc0c649c) — folded in here rather than a dedicated skill since it's pure methodology with no concrete tooling of its own.)
- Check scope rules against the program (in-scope domains, excluded assets, reward tiers) before testing anything.
- Identify parameters, forms, file upload points, and auth flows per target host — these are where most bug classes live.
- Run **hidden/undocumented-parameter discovery** (→ `hidden-parameter-discovery-testing`) against every prioritized endpoint before assuming its input surface is limited to what the rendered form/UI shows — feeds directly into `http-parameter-pollution-testing`, `mass-assignment-testing`, `web-cache-poisoning-testing`, and standard SQLi/XSS testing once a candidate parameter turns out to be live.
- Run the client-side "unhide" bookmarklet (→ `advanced-access-control-testing` entry #6) against every distinct page template as a cheap first pass — disabled fields, hidden buttons, and grayed-out premium/admin sections re-enabled this way frequently reveal a live endpoint the frontend just never links to, which is worth its own row in the prioritized target list.
- If a registration/signup flow exists, treat it as its own priority target (see `registration-flow-testing` in Phase 3) and enumerate every registration endpoint variant (web, mobile, API, legacy), not just the linked one — different implementations commonly have inconsistent validation.
- Cross-reference tech stack findings against known CVEs for that stack/version — once a specific product/version is fingerprinted, run a tag-scoped Nuclei scan directly against it (`nuclei -tags <product> -es info`); see `recon-scanning-toolkit`'s "mass CVE hunting via Shodan facet analysis + Nuclei tag scan" technique for the full command and for the Shodan-wide variant when hunting a known CVE across a whole ASN/IP range instead of just this one target.

## Phase 3 — Vulnerability Testing (per class)

Goal: systematically test each relevant vuln class against prioritized targets, rather than randomly poking.

Common classes to work through per target (not exhaustive — pull in a topic skill for depth on any of these when one is available; see "Linked technique skills" below for what currently exists):
- Injection: **SQLi + WAF-bypass tamper strategy** (→ `sqli-waf-bypass-testing`) whenever a SQLi candidate gets blocked/403'd or the target sits behind a known WAF, **NoSQL injection** (→ `nosql-injection-testing`) on any MongoDB-backed/JSON-body login, search, or password-reset endpoint, command injection, SSTI, **file upload → RCE/webshell** (→ `file-upload-testing`) on any file/image/document/avatar upload feature
- Access control: IDOR, broken authz, privilege escalation, **advanced GUID-based IDOR/BOLA** (→ `advanced-access-control-testing`) on targets using UUIDs/GUIDs or multi-tenant architecture, **mass assignment** (→ `mass-assignment-testing`) on any signup/registration/profile-update endpoint accepting JSON, **403/401 bypass** (→ `403-bypass-testing`) on any path found via dir-bruteforce/JS-analysis that returns 403/401 instead of 404
- Auth: **broken auth flows, session persistence/rotation, JWT revocation, remember-me tokens, email-verification/password-reset token logic** (→ `session-auth-testing`), **JWT forgery — algorithm confusion, jwk/kid/jku/x5u header injection, weak-secret brute-force** (→ `jwt-attack-testing`) on any JWT-issuing target, **OAuth `redirect_uri` validation bypass leading to authorization-code theft/ATO** (→ `oauth-redirect-uri-bypass-testing`) on any `/authorize`/SSO endpoint accepting a `redirect_uri` parameter, **cross-tenant SSO/IdP authentication confusion — substituting a self-controlled tenant's identity provider into a victim tenant's login flow** (→ `sso-cross-tenant-testing`) on any multi-tenant B2B SaaS offering per-organization enterprise SSO/SAML/OIDC, **registration/signup-flow-specific bugs** (→ `registration-flow-testing`) on any signup form, **WordPress XML-RPC abuse** (→ `xmlrpc-abuse-testing`) whenever `/xmlrpc.php` is reachable on a confirmed WordPress target
- Client-side: XSS (reflected/stored/DOM), CSRF, **clickjacking + HTTP security-header audit** (→ `security-headers-testing`) on every target as a near-zero-effort `curl -I` pass, **open redirect** (→ `open-redirect-testing`) on any return/continue/redirect-shaped parameter, **WebSocket XSS/CSWSH/auth bypass** (→ `websocket-security-testing`) on any real-time/chat/live-update feature, **CSP-misconfiguration-enabled DOM XSS** (→ `csp-misconfig-xss-testing`) on any reflected-parameter sink, **postMessage origin-validation/wildcard-broadcast bugs** (→ `postmessage-xss-testing`) on any iframe/popup/OAuth-callback cross-window messaging, **blind XSS via OOB callback** (→ `blind-xss-testing`) on any contact/feedback/support-ticket/file-upload form whose input is reviewed elsewhere (admin panel, logs, email), **stored-XSS render-surface mapping** (→ `stored-xss-mapping-testing`) on any persisted user-controlled field to find every place it renders, not just the first one checked
- Server-side: **SSRF** (→ `ssrf-testing`) on any url/webhook/callback/import-shaped parameter, **XXE** (→ `xxe-injection-testing`) on any XML/SOAP/SVG/DOCX-accepting endpoint, **RCE via command injection/SSTI/deserialization** (→ `rce-exploitation-testing`) whenever input reaches a shell command, template `render()` call, or deserializer, **Host header injection** (→ `host-header-injection-testing`) on any password-reset/email-verification flow, CDN-fronted target, or multi-tenant app with host-dependent behavior, **CRLF/HTTP response splitting** (→ `crlf-injection-testing`) on any parameter or path segment reflected into a response header, **compression side-channel attacks** (→ `compression-side-channel-testing`) on any gzip/brotli-compressed endpoint reflecting user input alongside a persistent secret (CSRF token, session ID)
- Access control (cross-origin): **CORS misconfiguration** (→ `cors-misconfig-testing`) on any browser-reachable API endpoint returning session/PII data
- Mobile (if an app is in scope): hardcoded secrets, missing SSL pinning, insecure local storage, deep link/intent abuse, WebView XSS (→ `mobile-app-testing`)
- Business logic: **race conditions** (→ `race-condition-testing`), **coupon abuse/payment manipulation/workflow-step bypass/state-field tampering** (→ `business-logic-abuse-testing`) on any checkout/cart/coupon/subscription/multi-step flow, **rate-limit bypass** (→ `rate-limit-bypass-testing`) whenever a brute-force/OTP-guessing/enumeration attack is blocked by an active rate limiter
- Info disclosure: verbose errors, exposed secrets, **GitHub recon for leaked secrets/credentials** (→ `github-recon-testing`) on every target as a standing parallel recon track, **live `.git/` repository disclosure** (→ `recon-scanning-toolkit`'s Git-repository-disclosure section + `github-recon-testing`'s dump/restore workflow) on any host serving an exposed `.git/` directory, **subdomain takeover** (→ `subdomain-takeover-testing`, detection command lives in `recon-scanning-toolkit`) run against the full Phase 1 subdomain list — cheap and high-confidence once that list already exists, **cloud storage bucket recon/misconfiguration** (→ `cloud-storage-bucket-testing`) whenever the stack references AWS S3/Azure Blob/GCS, **path/directory traversal** (→ `path-traversal-testing`) on any file-path/download/image/doc/log parameter, **web cache deception** (→ `web-cache-deception-testing`) on any CDN-fronted target with authenticated PII pages (`/account`, `/profile`, `/dashboard`), **web cache poisoning via unkeyed inputs** (→ `web-cache-poisoning-testing`) on any CDN/reverse-proxy-fronted target

For each class you test, check whether a linked technique skill exists (by name or description) for that specific class or tool — apply its payloads/methodology instead of relying on generic knowledge alone, since those skills capture techniques the hunter has personally validated as effective.

**Cross-cutting bypass technique — HTTP Parameter Pollution:** when a payload for any of the classes above gets blocked by a WAF/filter, or a validation check passes but you suspect the business logic reads a different value than the validator, retry using `http-parameter-pollution-testing` (duplicate the parameter so the filter sees a safe value and the backend uses the malicious one) before concluding the endpoint is safe. This applies across Injection, Access control, Auth (esp. CSRF/OAuth), Client-side (XSS filter bypass), and Business logic (price/role override) — it's not its own vuln class, it's a technique layered on top of testing the others.

**Cross-cutting bypass technique — WAF/CDN origin-IP discovery:** when the target sits behind a known WAF/CDN and payloads for *any* class above are getting blocked at the edge (generic 403/406 block pages), run `waf-origin-ip-discovery-testing` (ideally pre-emptively during Phase 1) to find and verify the real backend IP, then route traffic directly to it to bypass the WAF entirely for the rest of testing — cheaper than fighting WAF signatures payload-by-payload once an origin IP is confirmed.

## Phase 4 — Validation & Impact

Goal: confirm the bug is real and establish real-world impact before writing it up.

- Reproduce reliably — document exact steps.
- Establish impact: what can an attacker actually do with this (data exposure scope, account takeover, financial impact)?
- Check for related/chained issues nearby (one bug often reveals a sibling).
- If a Phase 3 finding results in shell/SSH/code execution access, consult `post-access-impact` here — it's the checklist for turning raw access into a reportable, high-severity finding without crossing into destructive/unauthorized territory.
- **Don't stop at the first working PoC — escalate to business-critical systems before writing anything up.** Reading `/etc/passwd` via LFI or hitting an exposed `.env` is the *start* of impact-proving, not the end: push further toward cloud metadata endpoints, environment-variable extraction, internal admin dashboards, or customer PII access. The gap between "theoretical file read" and "confirmed customer PII exposure" is routinely the gap between a $500 and a $10,000 payout for what is nominally the same underlying bug.
- **If credentials are exposed, validate them safely (minimum access only) and note explicitly whether they're still active** — an inactive/rotated key and a live production key are wildly different severities even though the "finding" (a key in a JS bundle/`.env`) looks identical on the page.
- **Record a video PoC for anything time-sensitive or hard to convey in a screenshot sequence** (active credential access, a live dashboard export, a race-condition win) — a triager questioning whether a finding is "really" exploitable is far less likely to argue with a frame-by-frame video than a written step list.
- Source: [How to Translate Bug Impact into Business Risk](https://freedium-mirror.cfd/https://medium.com/@Aacle/how-to-translate-bug-impact-into-business-risk-50d6efe525d7).

## Phase 5 — Reporting

Goal: write a report that gets triaged fast and rated fairly.

- Clear title stating the vuln class and affected component.
- Steps to reproduce, numbered, minimal and exact.
- Impact statement in terms the program will care about (not just "this is bad" — explain what an attacker gains).
- Suggested fix/remediation if known.
- Attach proof (screenshots, request/response pairs, video for anything hard to convey in text).
- **Write the impact section in business-risk language, not a CVSS score.** A CVSS calculator is a technical measure, not a measure of business reality — a "low severity" info-disclosure finding that happens to expose live production AWS keys is not low severity to the company reading the report, regardless of what the calculator says. If you find yourself leaning on the calculator's number to argue severity, that's a signal to dig for more impact before submitting, not to submit as-is.
- **For exposed/live credentials specifically, state the incident-response trigger explicitly rather than just describing the leak:** e.g. *"These credentials are currently active. Your Incident Response team needs to investigate this immediately to determine how long they have been exposed, who else has accessed them, and whether they need to be rotated."* This framing forces a triager to route the report to IR/security rather than filing it as routine info-disclosure.
- **Self-check before submitting:** "If I were the CEO of this company, would this report make me panic?" If the honest answer is no, the finding likely needs another round of escalation (see Phase 4) before it's ready to file.
- **Info-disclosure-specific self-check before submitting anything in that class:** "in what way can an actual attacker use this information?" — a version banner, a stack trace, or an internal hostname is only reportable once you can name the concrete next step it enables (a CVE it's actually vulnerable to, a credential it reveals, an endpoint it points at); banner-grabbing/version disclosure with no demonstrated actionable follow-on is routinely marked informative/out-of-scope, so push for that follow-on before submitting rather than reporting the exposure alone.

## Linked technique skills

Topic skills currently available (each accumulates techniques from multiple source writeups on that topic — check them for updates before relying on generic knowledge alone). Grouped below by where in the workflow each one applies — same category breakdown as the Phase 3 bullet list above — so the ordering itself tells you the sequence to reach for them in, not just what each one does.

### Meta / tooling (apply from Phase 0 onward)
- `claude-code-burp-mcp-workflow` — meta/tooling skill (not a vuln class): wiring Claude Code directly into Burp Suite's proxy history via MCP (`claude mcp add burp --transport sse ...`), then running the engagement through a four-phase prompt structure (traffic analysis → attack surface mapping → active testing → report generation) with an evidence-first validation gate before trusting any Claude-proposed finding, plus a no-MCP fallback for raw saved requests/JS files. Apply at the very start of an engagement, alongside Phase 0/1, to decide how Claude itself gets looped into the rest of this workflow — it's how you run the other topic skills through Claude faster, not a replacement for them.

### Recon & asset discovery (Phase 1)
- `recon-scanning-toolkit` — concrete command-line toolchain (not methodology) for subdomain enum (subfinder/assetfinder/amass/crt.sh), live-host probing (httpx), URL collection (katana/gau/gospider), Wayback Machine CDX API deep-dive, mass CVE hunting via Shodan facet analysis + tag-scoped Nuclei scans, and automated scanning (dalfox, nuclei, sqlmap, qsreplace for SSRF/redirect, tplmap, jwt_tool, gowitness), plus a manual bypass checklist (boring endpoints, trusted-header spoofing, error-message reading). Apply throughout Phase 1-3 whenever the hunter needs the actual shell command for a step rather than just the methodology.
- `subdomain-takeover-testing` — dangling-CNAME subdomain takeover: Subzy/Subjack detection (command lives in `recon-scanning-toolkit`), manual verification against "Can I Take Over XYZ?", the non-destructive hidden-comment proof-of-control PoC standard, and the 5-point post-takeover escalation checklist (OAuth-redirect-token theft, cross-subdomain cookie theft, CSRF via SameSite=Lax, CORS/CSP allowlist bypass — the last one being a full supply-chain-severity JS-injection chain). Apply during Phase 1/3 against the full subdomain list on every target.
- `waf-origin-ip-discovery-testing` — finding and verifying a WAF/CDN-fronted target's real origin IP (Shodan SSL-cert search, Censys, SecurityTrails, favicon-hash pivoting via Fofa/ZoomEye, VirusTotal/AlienVault) then routing traffic directly to it to bypass the WAF entirely. Apply during Phase 1 (pre-emptively, as soon as a WAF/CDN is confirmed) and as a cross-cutting Phase 3 bypass whenever WAF blocks impede testing of any vuln class.
- `github-recon-testing` — GitHub-based secret/credential recon: search operators (`filename:`/`extension:`/`path:`/`repo:`/`language:`), a full secret-category keyword taxonomy, GitGraber/TruffleHog automation, live-target `.git/` exposure+dumping (GitTools/git-dumper/DotGit, repo-structure restoration), a systematic local source-tree secret-scanning checklist for once code is actually in hand (grep/regex sweeps, `git log -p` history mining, gitleaks/detect-secrets/GitGuardian, dotfiles, comments, dependency/vendor trees, IaC files), and Keyhacks-based key validation before reporting. Apply during Phase 1 (standing parallel recon track on every target) and Phase 3, Info disclosure testing.
- `cloud-storage-bucket-testing` — cloud object-storage bucket recon and exploitation: Google dorking, subdomain/JS-file S3 URL extraction, bucket-name brute-forcing/permutation (LazyS3, Cewl+S3Scanner), GitHub secret search, public bucket databases (GrayhatWarfare, osint.sh), and unauthenticated AWS CLI list/read/write/delete testing; generalizes to Azure Blob/GCS. Apply during Phase 1 (discovery) and Phase 3, Info disclosure/Access control testing, whenever the stack references AWS S3/Azure Blob/GCS.
- `application-dos-testing` — application-level DoS within bug-bounty scope: Shodan IP-range banner-anomaly hunting to find legacy/non-standard HTTP server software, then a minimal-connection-count PoC (5-20 held-open requests) confirming a missing-timeout/connection-exhaustion defect. Apply during Phase 1 (Shodan `net:` sweep of the target's own IP range for banner outliers) and Phase 3, Availability testing — always check the program's scope for DoS-category exclusions first.
- `supply-chain-attack-recon` — public-artifact-only supply-chain recon: dependency confusion via leaked internal package-scope names (GitHub org/repo mining → registry 404 check → build-system-misconfiguration confirmation), GitHub Actions workflow injection (`pull_request_target` + untrusted `${{ github.event.* }}` interpolation, mutable-tag action pinning), SBOM/CycloneDX-SPDX version mining cross-referenced against osv.dev, and container-registry/image-layer secret exposure (`docker save` + trufflehog). Recon-only scope — identifying an unclaimed internal package name or an injectable workflow is reportable; actually publishing/triggering either requires separate written authorization. Apply during Phase 1 (standing parallel recon track whenever a target has a public GitHub org, SBOM releases, or public container images) and Phase 3, Supply-chain testing.

### Platform/target-category fingerprint checks (Phase 1, run once the tech stack is known)

### Enumeration & prioritization (Phase 2)
- `hidden-parameter-discovery-testing` — finding undocumented parameters (query/body/JSON/header/cookie) the frontend never sends but the backend still reads: Arjun/x8/Burp Param Miner/GAP automation, JS-file and HTML hidden-input candidate-name sourcing, Google dorking + Wayback historical-JS-diffing for discontinued-but-still-live parameters, and cross-endpoint parameter reuse. ### Injection (Phase 3)
- `sqli-waf-bypass-testing` — sqlmap + Ghauri command reference for SQLi exploitation and WAF evasion: tamper-script combos mapped to specific WAF vendors, WAF body-inspection-size-limit exhaustion, origin-IP discovery to route around the WAF, and dual-tool strategy. Apply during Phase 3, Injection testing, whenever a SQLi candidate is blocked by a WAF or the target's fingerprinted WAF vendor is known.
- `nosql-injection-testing` — MongoDB-focused NoSQL injection: `$ne`/`$gt` operator-injection auth bypass (JSON body and bracket-notation query params), `$where`-clause server-side JS code injection via string concatenation, time-based blind extraction via `$where`+`sleep()`, and second-order NoSQL injection. Apply during Phase 3, Injection testing, on any MongoDB/NoSQL-backed login, search, or password-reset endpoint accepting JSON.
- `xxe-injection-testing` — XML External Entity injection: `<!DOCTYPE>`/`<!ENTITY>` payload syntax for local file disclosure, SSRF/cloud-metadata chaining via an entity URL (hands off to `ssrf-testing`'s metadata methodology once confirmed), blind/OOB exfiltration via a parameter entity pointing at an attacker-hosted DTD, filter-bypass encodings (parameter entities, external-DTD hosting, UTF-7), PHP protocol-wrapper escalation to RCE (`expect://`), and the billion-laughs DoS variant. Apply during Phase 3, Server-side testing, on any XML/SOAP/SVG/DOCX-accepting endpoint.
- `rce-exploitation-testing` — RCE investigation methodology (trace data flow from input to sink before injecting, non-destructive PoC discipline, RCE-vs-privilege-level and vulnerability-type-vs-confirmed-impact distinctions) plus command-injection detection (separator variants `;`/`&&`/`||`/`|`, blind/timing confirmation via `sleep`) and SSTI detection (`{{7*7}}` arithmetic-evaluation probe). Apply during Phase 3, Server-side testing, whenever input reaches a shell command or template engine; cross-references `file-upload-testing`/`ssrf-testing`/`path-traversal-testing`/`sqli-waf-bypass-testing`/`mass-assignment-testing` for the other RCE-adjacent vectors those skills already own. Unsafe deserialization/gadget chains and zip-slip archive extraction are named as gaps pending a source with concrete payloads.
- `ssrf-testing` — SSRF command reference: parameter identification, cloud-metadata targeting (169.254.169.254 + IAM credential theft), local/internal-network probing, IP-filter bypass encodings (hex/octal/IPv6/shortened), Next.js-specific SSRF surface (Image Optimization API, Middleware `Location`-header CVE-2025-57822, Server Actions redirect-validation-bypass CVE-2024-34351), and Interactsh/Collaborator-based blind confirmation. Apply during Phase 3, Server-side testing, on any url/webhook/callback/import-shaped parameter, or any Next.js-fingerprinted target.
- `file-upload-testing` — upload filter bypass (double extensions, null byte, magic-byte spoofing, case sensitivity) to achieve webshell RCE, plus filename-based path traversal/XSS and SVG script injection. Apply during Phase 3, Injection/Client-side testing; flag any upload feature during Phase 1/2 recon as a priority target.
- `crlf-injection-testing` — CRLF (`%0d%0a`) injection into response headers: header injection, session fixation via forced `Set-Cookie`, full response splitting escalating to XSS/full-page iframe phishing, cache poisoning, open-redirect-via-`Location`, plus GBK multi-byte-encoding filter bypass and a full payload catalog by category. Apply during Phase 3, Server-side/Client-side testing, on any parameter or path segment reflected into a response header.
- `host-header-injection-testing` — Host/`X-Forwarded-Host` header-trust exploitation: parsing-confusion payload variants (whitespace, duplicate headers, absolute-URL, blank value, IP substitution, encoding), password-reset-link poisoning, web cache poisoning, SSRF via Host header, and virtual-host/access-control bypass. Apply during Phase 3, Server-side/Client-side testing, on password-reset/email-verification flows, CDN-fronted targets, or multi-tenant apps with host-dependent behavior.

### Access control (Phase 3)
- `advanced-access-control-testing` — advanced IDOR/BOLA for GUID/UUID-based targets: leaking unpredictable IDs (mobile traffic, exports, error messages), cross-tenant BOLA via missing tenant scoping, blind IDOR via timing/state-change side channels, access-control-filter bypass via parameter pollution/JSON type juggling, UUIDv1 time-based prediction, unhiding client-side-disabled/hidden DOM elements to surface missing server-side authorization, static-keyword substitution (`me`/`my`/`current` → literal ID), second-order path traversal through a privileged-shared-token middleware layer, session poisoning via a reused session variable, and multi-step-workflow ownership-transfer logic flaws. Apply during Phase 2 (the unhide-bookmarklet pass, as a cheap enumeration step) and Phase 3, Access control testing; flag any target using GUIDs for object IDs or with multi-tenant/B2B architecture during Phase 1/2 as a priority for the IDOR/BOLA techniques specifically.
- `mass-assignment-testing` — injecting unauthorized JSON fields (isAdmin, role, plan, org_id, email_verified, provider) into signup/profile-update endpoints to hit backend auto-binding; payload catalog covers casing/type variants, prototype pollution, dot-notation nesting, array wrapping, NoSQL operators, Content-Type fallback tricks, and string-encoded nested JSON. Apply during Phase 3, Access control/Business logic testing, on any JSON-accepting registration or account-write endpoint.
- `403-bypass-testing` — bypassing a 403/401 response on a discovered-but-blocked path: HTTP method tampering, trusted-header spoofing (`X-Original-URL`/`X-Rewrite-URL`/`X-Forwarded-For`), path encoding/case/obfuscation tricks, parameter tampering, JWT `alg:none` tampering, null byte injection, HTTP/1.0 downgrade, and Wayback Machine recon for since-restricted endpoints. Apply during Phase 3, Access control testing, on any path found via dir-bruteforce/JS-analysis that returns 403/401 instead of 404.
- `cors-misconfig-testing` — probing Access-Control-Allow-Origin reflection combined with Access-Control-Allow-Credentials:true, which lets an attacker-hosted page read authenticated cross-origin responses; covers curl/Corsy/CORScanner commands, null-origin/subdomain/substring/browser-specific-character bypass variants (incl. a ready-to-use sandboxed-iframe null-origin PoC template), and SSRF-via-CORS escalation into internal-only resources. Apply during Phase 3, Access control testing, on any browser-reachable API endpoint returning session/PII data.

### Auth (Phase 3)
- `session-auth-testing` — 14-point checklist for session/auth lifecycle bugs: session persistence after logout/password-change, session fixation, no rotation on privilege escalation, concurrent-session abuse, weak remember-me tokens, unrevoked JWTs, cached authenticated pages via back button, and email-verification/password-reset token logic flaws (incl. pre-account-takeover). Apply during Phase 3, Auth testing, on any target with login/logout, password reset, email verification, remember-me, or JWT flows.
- `jwt-attack-testing` — JWT forgery attack surface beyond revocation: `alg:none`/missing-signature-verification, RS256→HS256 algorithm confusion, `jwk`-header key injection (CVE-2018-0114-style), `kid`-header path-traversal/SQLi, `jku`/`x5u`-header SSRF fetching an attacker-controlled signing key, and weak-HMAC-secret brute-forcing (John/jwt_tool). Apply during Phase 3, Auth/Server-side testing, on any target issuing JWTs.
- `oauth-redirect-uri-bypass-testing` — OAuth 2.0/OIDC `redirect_uri` validation-bypass technique library: prefix/substring/regex/domain-suffix matching flaws, path-traversal into an internal open-redirect utility reachable under the registered callback prefix, subdomain injection, and userinfo/`@`-trick payloads, all aimed at leaking the authorization code/token to attacker infrastructure for full account takeover. Apply during Phase 3, Auth testing, on any `/authorize`/SSO endpoint accepting a `redirect_uri` parameter; cross-references `open-redirect-testing` for internal open-redirect discovery and `race-condition-testing` for the separate OAuth account-linking TOCTOU bug class.
- `sso-cross-tenant-testing` — cross-tenant SSO/IdP authentication-confusion technique library for multi-tenant B2B SaaS: substituting an attacker's own self-controlled identity provider (configured under their own trial tenant) into a victim tenant's login flow to mint an authenticated session as any email they choose, rooted in five missing server-side bindings (SSO-config-to-tenant, login-transaction-to-tenant, IdP-to-tenant, auth-response-to-transaction, identity-resolution-to-tenant). Apply during Phase 3, Auth testing, on any target offering per-organization enterprise SSO/SAML/OIDC, especially where self-service trial-org creation is possible; distinct from `oauth-redirect-uri-bypass-testing` (single-tenant redirect_uri manipulation) and `race-condition-testing`'s OAuth-linking entry (TOCTOU, not a binding gap).
- `registration-flow-testing` — registration/signup-specific checklist: duplicate-registration overwrite, DoS via oversized input, missing rate limiting on signup/OTP, stored XSS in registration fields, reserved-username route collision, hidden/legacy registration endpoints with inconsistent validation, weak/predictable verification-link tokens, punycode/IDN homograph takeover, OTP brute-force, null byte injection. Apply during Phase 2 (enumerate every registration endpoint variant) and Phase 3, Auth testing; cross-references `session-auth-testing`, `mass-assignment-testing`, `http-parameter-pollution-testing`, and `advanced-access-control-testing` for overlapping general techniques rather than duplicating them.

### Client-side (Phase 3)
- `csp-misconfig-xss-testing` — DOM-XSS hunting via reflected URL parameters (full source/sink taxonomy: `location.hash`/`.search`, `document.referrer`, `window.name` as sources; `innerHTML`, `eval`/`Function`, `document.write`, jQuery sinks, AngularJS CSTI as sinks), context-specific payload construction (HTML/attribute/JS-block/textarea), and checking whether the target's CSP header (e.g. `'unsafe-inline'`) actually blocks the resulting script or is bypassable (Report-Only trap, vulnerable-CDN-library/JSONP-on-allowlisted-host, predictable nonces, CSP injection). Apply during Phase 3, Client-side testing; also worth a cheap `curl -I` CSP-header sweep across all Phase 1/2 recon hosts to flag high-value targets early.
- `postmessage-xss-testing` — cross-window `postMessage` communication bugs: missing/weak `event.origin` validation on message listeners (incl. prefix/substring-matchable regex bypasses), wildcard (`'*'`) `targetOrigin` senders leaking tokens/PII to any listening origin, and the resulting DOM-XSS/OAuth-token-theft/forged-message-auth-bypass chains. Apply during Phase 3, Client-side testing, on any target using iframes, popups, or OAuth/SSO callback flows.
- `blind-xss-testing` — injecting XSS payloads into inputs that render somewhere you can't see (logs, admin panels, email, file/EXIF metadata), caught via an OOB callback server (XSS-Hunter-Express/xss.report); covers header-based injection via Burp Match & Replace, bulk injection with subfinder/gau/bxss, Arjun for hidden-parameter discovery, EXIF-metadata payload embedding, and PasteJacking (clipboard text/html injection). Apply during Phase 3, Client-side testing, on any contact/feedback/support-ticket/file-upload/rich-text form.
- `stored-xss-mapping-testing` — five-step methodology for finding every place a piece of stored user-controlled data actually renders (not just the field's own page): overlooked-field inventory (org names, filenames, webhook labels, bulk-import paths), per-field unique markers, exhaustive render-surface sweep (list/detail/search/autocomplete/email/export-CSV-PDF-XLSX/print/embed/admin views), two-account self-XSS-vs-stored-XSS validation, and audience-based severity ranking (self-only → invited → all-users → cross-tenant → staff/admin). Apply during Phase 3, Client-side testing, on any target with persisted user-controlled fields; distinct from `blind-xss-testing`'s genuinely-invisible-surface OOB capture and `csp-misconfig-xss-testing`'s reflected/DOM payload construction.
- `security-headers-testing` — HTTP security-header + browser-isolation-policy audit: `X-Frame-Options`/`frame-ancestors` (clickjacking, with a working iframe-overlay PoC template), `Strict-Transport-Security`, `X-Content-Type-Options`, cookie `Secure`/`HttpOnly`/`SameSite` flags (incl. a full CSRF-exploitability checklist and per-value SameSite breakdown), and `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy`/`Cross-Origin-Resource-Policy`, plus vulnerable-client-side-library detection (Retire.js/`npm audit`/Burp DOM Invader) riding along on the same pass — explicitly cross-references `csp-misconfig-xss-testing`/`cors-misconfig-testing`/`session-auth-testing` for the header-adjacent items those skills own instead of duplicating them. Apply during Phase 3, Client-side testing, on every target as a near-zero-cost `curl -I` sweep — works even on purely static sites with no backend logic.
- `open-redirect-testing` — mass redirect-parameter discovery (large keyword sweep + gf redirect) and qsreplace+httpx confirmation pipelines; escalate severity when the redirect sits inside an OAuth redirect_uri/SSO callback. Apply during Phase 3, Client-side/Business-logic testing, on any return/continue/redirect-shaped parameter.
- `websocket-security-testing` — WebSocket XSS, Cross-Site WebSocket Hijacking (CSWSH), per-message authorization bypass/IDOR, missing authentication, hidden/undocumented actions, and resource-exhaustion via payload flooding. Apply during Phase 3, Client-side/Auth/Access-control/Availability testing; also flag during Phase 1/2 recon any target with chat/live-update/real-time features (look for `101 Switching Protocols` / `wss://` traffic) as a priority for this technique.
- `email-field-injection-testing` — field-specific test matrix for any email input (signup, login, password reset, contact form, invite-a-friend, profile update): SSRF via the email's domain part triggering an outbound verification/lookup request, OS command injection confirmed via OOB-canary domain in shell-metacharacter payloads, RFC822 malformed-but-accepted format-bypass strings, and downstream CSV/log injection on export/logging — plus a routing table sending the overlapping classes (XSS, CRLF, SQLi, open redirect, homograph, rate-limit bypass) to their existing deep-dive skills. Apply during Phase 2/3 whenever ANY field on the target accepts an email address, not just the primary signup form.

### Server-side / cache (Phase 3)
- `web-cache-deception-testing` — tricking a CDN/cache layer into storing an authenticated, sensitive response as a static asset (file-extension appending, delimiter path confusion, encoded path traversal, header manipulation), then reading it back unauthenticated. Apply during Phase 3, Info disclosure/Access control testing, on any CDN-fronted target with authenticated PII pages.
- `web-cache-poisoning-testing` — the inverse bug from WCD: finding unkeyed inputs (a large header taxonomy incl. `X-Forwarded-Host`/`X-Forwarded-Scheme`/`X-Original-URL`, cache-key normalization mismatches like path traversal/port confusion, fat-GET/body-in-GET, multi-layer CDN+application chaining, header-normalization dash/underscore bypass, and CPDoS via method-override) that the origin processes but the cache key ignores, then poisoning a cacheable response so every subsequent visitor is served the attacker-controlled version; includes WAF-evasion variants (duplicate headers, encoding, protocol-list confusion) and Param Miner automation. Apply during Phase 3, Server-side/Client-side testing, on any CDN/reverse-proxy-fronted target.
- `compression-side-channel-testing` — BREACH/CRIME/HEIST-style compression side-channel attacks: recovering a secret (CSRF token, session ID, API key) reflected alongside attacker-controlled input in the same compressed HTTP response, purely by measuring response-size deltas across incremental guesses. Apply during Phase 3, Server-side/Client-side testing, on any gzip/brotli-compressed endpoint that reflects user input into the same response body as a persistent secret.

### Business logic (Phase 3)
- `race-condition-testing` — TOCTOU/race condition exploitation (OAuth/SSO account-linking, single-use tokens, coupons, balances). Apply during Phase 3, Business-logic/Auth testing; also flag during Phase 1/2 recon when a target has SSO or single-use-token flows, since those endpoints should be prioritized for this technique early.
- `business-logic-abuse-testing` — coupon/discount abuse, payment/price manipulation, workflow/sequence-step bypass, client-controlled state-field tampering, and differential validation across multiple entry points writing to the same field, all rooted in trusting frontend-supplied values instead of server-side re-validation. Apply during Phase 3, Business-logic testing, on any checkout/cart/coupon/subscription/multi-step-wizard flow; cross-references `race-condition-testing` for the concurrency angle on the same endpoints.
- `rate-limit-bypass-testing` — bypassing an *active* rate limiter (not detecting a missing one — see `registration-flow-testing` for that): trusted-IP header spoofing, real IP rotation (proxychains/`ip-rotate`/AWS API Gateway), User-Agent randomization, HTTP method/parameter-name/encoding/case variation, parameter pollution, alternate-endpoint discovery, timing/slow-drip pacing, and CAPTCHA-bypass tooling. Apply during Phase 3, Business logic/Auth testing, whenever a brute-force/OTP-guessing/enumeration attack is blocked by a rate limiter (login, OTP/2FA, password reset).

### Info disclosure (Phase 3)
