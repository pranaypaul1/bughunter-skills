# loxs-hackerone — processed report log

This is not where techniques live — it's an index, exactly like `loxs-medium` but for HackerOne public disclosed reports instead of Medium articles. Run this exact pipeline every single time the hunter shares a new HackerOne report URL (via `/loxs-hackerone <url>` or by pasting a `hackerone.com/reports/...` link and asking to process it). Don't skip steps or improvise a different flow.

**Shared destination, separate log:** this skill and `loxs-medium` feed the exact same pool of topic skills (`race-condition-testing`, `ssrf-testing`, `path-traversal-testing`, etc.) — a technique doesn't care whether it came from a blog post or a disclosed report. Keep tracking which *source* has been processed in each skill's own table (this file tracks HackerOne report URLs, `loxs-medium` tracks article URLs), but route both into the same topic-skill set in Step 3 below. Never create a "HackerOne-only" duplicate of a topic skill that already exists from a Medium source, or vice versa.

## Step 1 — Check the log first

Before fetching anything, check the "Processed reports" table below for the URL (match on the report ID — `hackerone.com/reports/123456` — since the same report can be linked with or without a slug/title suffix). If it's already there, tell the hunter it's already been processed and point to the topic skill — don't reprocess.

## Step 2 — Fetch the report content

1. Try `WebFetch` on the URL first (fast path) — but expect it to fail or return an empty/JS-shell page more often than with Medium articles: HackerOne's report pages are a heavily client-side-rendered React app, and the raw HTML WebFetch sees before JS execution is frequently just a loading shell.
2. If `WebFetch` fails, errors, or returns clearly broken/empty content (no report body, no timeline, a bare app shell, a login wall), fall back to Chrome browser automation: load the Chrome tools (ToolSearch for `mcp__claude-in-chrome__*` core set), open the URL in a new tab, wait for the page to fully render, and read the rendered page content from there instead. A report that's genuinely private/not disclosed will show an access-denied state in Chrome too — if so, tell the hunter it isn't public and stop (don't guess at content).
3. Either way, extract:
   - **Report metadata**: report ID, title, program/team name, reporter, submission date, current state (Triaged/Resolved/Informative/Duplicate/etc.), severity rating (and CVSS vector if the program uses one), bounty amount awarded, weakness/CWE tag HackerOne assigned.
   - **Vulnerability class/root cause**: what the bug actually is, in the reporter's own technical terms.
   - **Methodology**: how the reporter found it — recon steps, what made them suspect this endpoint/parameter, any tools named.
   - **Exploitation steps**: the exact numbered reproduction steps from the report body, and every literal request/payload/URL/code snippet shown — same standard as `loxs-medium` Step 2.3, matching the technical detail bar set in `race-condition-testing`.
   - **Program/triager discussion**: read the activity/comment timeline too, not just the report body — triagers sometimes ask for (and get) a more damaging PoC mid-thread, or the reporter posts a refined payload after an initial "can't reproduce" — that follow-up content is often the highest-value technical detail in the whole report.
   - **Impact & resolution**: the reporter's stated impact, and how the program described the fix if mentioned.

## Step 3 — Identify the topic and route it

1. Determine which vuln class/technique category the report is really about (e.g. race condition, IDOR, SSRF, XSS, auth bypass) — same judgment call as `loxs-medium`.
2. Check whether a topic skill already exists for that category (search the same pool of topic skills `loxs-medium` routes into — check the current skill list, not just what's referenced from `loxs-medium`'s own log, since either log may have created a skill the other hasn't linked yet):
   - **Exists** → add a new dated, numbered entry to that skill's "Recorded techniques" section, following the same structure as existing entries (Where / Root cause / Exploit steps / Impact framing / Generalize note). Don't duplicate or create a second skill for the same topic. Cite the source as the HackerOne report (title + link + report ID), the same way Medium-sourced entries cite their article.
   - **Doesn't exist** → create a new topic skill directory under `~/.claude/skills/<topic-name>/SKILL.md`, mirroring the structure of `race-condition-testing` (frontmatter with a pushy trigger description, Core theory, Trigger technique, Recorded techniques).
3. Update `bughunting-workflow`'s "Linked technique skills" section: add a line naming the new/updated topic skill and which phase(s)/vuln class it applies to, if it isn't already listed there.
4. **Bounty/severity data point:** when a topic skill has an "Impact framing for report" or "bounty ranges" section, a real awarded-bounty figure from a disclosed HackerOne report is a stronger data point than an article's stated estimate — add it there (with the program name if the hunter would find that useful for calibration) rather than only logging it in this file's table.

## Step 4 — Log it here

Append a row to the "Processed reports" table below (date, report title+link+report ID, program, topic skill it fed into). This is what step 1 checks on future runs — never skip it.
